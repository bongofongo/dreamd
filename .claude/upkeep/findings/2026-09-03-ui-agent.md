## Pass 2 — findings

Ordered by what a reader would notice. Nothing here is a one-word fix except the
drift.

### A. Escape does not close the docked native pane

`wireKeys` returns on the first line of its keydown handler if the event came
from inside `#pty-pane` (5237, via `inTerminal` 4972). On the terminal surface
that is correct and load-bearing: xterm's `attachCustomKeyEventHandler`
(3988–4004) claims Escape and `toggle_pane` before they ever reach the document,
which is what the comment at 5268 means by "both paths end at `closePane`".

On the native surface xterm is never built, so that handler does not exist.
`#agent-input`'s own keydown (5104) claims Escape **only while `agent.busy`** —
which is right, an interrupt outranks a close — and lets an idle one propagate
to a document handler that drops it. Focus on any other node in the dock (a
permission card's Allow, `⟳`, the mode select) has no claimant at all.

So on the default surface, with the pane docked and focused, Escape does
nothing. D12 says Escape closes the pane in every mode; it currently closes it
in every mode but the default one. The same early return also swallows the zoom
keys there, which the comment at 5239 says are "claimed above everything".

Diff sketch: `inTerminal` means "in the agent dock", and the two callers want
different questions. `isEditable` (5219) wants the pane-wide answer and should
keep it. The keydown guard wants "this event is the child's", which is true only
of the terminal surface:

```js
// the child's keys, and only a terminal has a child that owns them
if (inTerminal(e.target) && !$("pty-pane").classList.contains("native")) return;
```

Everything after that line already handles the native pane correctly: Escape
falls to `closePane` at 5291, and `#agent-input` matches `isEditable` so no
bare-letter binding fires into it.

By eye: with `agent.surface` unset (native), open the pane, click the composer,
press Escape — the pane should hide, and a second Escape should leave view mode
alone. Then with `surface = "terminal"`, confirm Escape inside xterm still
closes and that `/`, `n`, `j`, `k` still reach the child.

### B. Confirming a mode change never restarts a native session

`stageModeChange` (4923) shows the confirm strip whenever `pty.running ||
agent.running`, and its sentence is explicit: "this restarts the session and the
conversation above is lost". `commitModeChange` (4949) then writes the config
and restarts on `if (pty.running || pty.term)` — neither of which is ever true
on the native surface.

So the reader is warned, accepts the cost, and keeps the old session running in
the old permission mode while the header select shows the new one. The mode does
take effect, but silently and only at the next spawn.

Diff sketch: one condition — `if (pty.running || pty.term || agent.running)
await restartPane();`. `restartPane`'s native arm (4093–4114) already does the
whole reset and re-spawn.

By eye: native surface, run one turn, switch the select, press Restart. The log
should clear and the session come back; today it does neither.

### C. The send bar's reason is terminal-only

`paintSendBar`'s `why` (3476) is a three-way on `pty.opening` / `pty.running`.
On the native surface `pty.running` is never set, so the middle branch —
"waiting for Claude Code to finish starting" — is unreachable, and any row that
outlives `pty.opening` reads "the pane is not running" even when the native
session is alive, or when it failed to start for a reason `pty.status` is
holding verbatim.

Diff sketch:

```js
const why = pty.opening ? "starting Claude Code"
  : !paneReady() ? (pty.status || "the pane is not running")
  : "waiting for Claude Code to finish starting";
```

`paneReady` (3404) is already the surface-aware predicate, and `pty.status` is
already the string the pop-out's hint prefers for exactly this case (4888).

### D. A submission whose pairs all vanished leaves a permanent row

`take_send` (main.rs:747–755) calls `flow.take_ready()`, which *removes* the
entry, and then returns `Ok(None)` if every pair has since been unstacked.
`releaseSend` (3411) reads `null` as "nothing armed, not an error" and returns
false, so `flow.pending` keeps a token Rust has already spent. `flowTick` never
empties, `stopFlowTimer` never fires, and the reader is left with a stale
"1 question queued" row and a 350ms interval for the rest of the session. Cancel
clears it — `cancel_send` returns false and the frontend deletes locally — but
the row claims a send is pending when none is.

Reachable only by deleting or unstacking every mark in a submission while it
waits on a cold start, which is narrow. Worth noting because the cost is a timer
that never stops and a bar that also lifts the toast row (`body.sending`).

A frontend-only fix is possible — if `paneReady()` and every entry is armed and
`take_send` hands back nothing, the tickets are spent — but the honest fix is one
bit from Rust distinguishing "nothing ready" from "the ticket is spent", and that
is `flow`/`main.rs`, i.e. areas 5 and 8. Flagged, not proposed.

### E. `pty.prefs` is cached per process and never re-read on `repo-changed`

`loadAgentPrefs` (3914) early-returns on a populated `pty.prefs`, and the
`repo-changed` handler (5035) re-reads the theme, the zoom and the tree but not
the agent prefs. `agent.position` and `agent.permission_mode` are launch-time and
staleness is defensible for a session already up — but `agent.popout` is neither,
and both it and `agent.surface` are keys a repo's `.dreamd.toml` may set
(`strip_untrusted` denies only `theme_css`, `permission_mode`, `menubar` and
`titlebar`). So walking into a repo that asks for `popout = "always"` gets the
dock for the rest of the session, and `paintMcpStatus`'s `!nativeSurface()`
branch decides on the previous repo's surface.

Diff sketch: null `pty.prefs` in the `repo-changed` handler when no session is
running (`!pty.running && !agent.running`), leaving the next open to re-read it.
Doing it unconditionally would let a live session's header disagree with the
session it is driving.

### F. Two small dead ends

- `focusAgent` (2385) falls back to `$("agent-log").focus()`. `#agent-log` has
  no `tabindex` (index.html:1906), so that call is a no-op — and it is
  unreachable anyway, since `focusAgent` only runs when the pane is shown and
  `#agent-input`'s `offsetParent` is then non-null. One line.
- `paintMcpStatus`'s doc says "**Nothing here has a button any more**" (4237)
  eleven lines above the `Copy` button it builds (4276–4287). The paragraph means the
  *Register* button, and says so two sentences later; the summary line is the
  part that reads false.

## Pass 3 — simplify

Two duplicates, both behaviour-preserving, ~14 lines net.

**`paintModelChips` is `paintModelChipsFrom(pty.model)`.** 4192 compares
`b.dataset.model === pty.model`; 4905 compares through `chipMatches`, which
lowercases the wire model and asks `includes(chip)`. For the three closed-enum
values the chips carry (`opus`, `sonnet`, `haiku`) and for `null`, the two agree
on every input. Delete 4192–4196 and give its two callers — 4047 in
`startPaneProcess` and 4182 in `setModel` — the `From` version, which
`restartPane`'s native arm already uses (4110).

**`MODE_LABELS` restates the four `<option>` texts.** 3759–3764 maps each
`agent.permission_mode` spelling onto a label that is already the option's own
text in index.html:1868–1871 — character for character, all four. Its one reader
is `stageModeChange`'s sentence (4932). Reading the label off the select removes
the second copy and the drift risk between them:

```js
const label = $("pty-mode").selectedOptions[0]?.textContent || next;
```

The doc comment above `MODE_LABELS` is worth keeping in some form — it is the
one place that says the `<option>` value is the config spelling with no
translation table in between, which is exactly why this works.

## Noted, not proposed

- `.agent-card` (the permission card, index.html:841) and `#agent-card` (the
  pop-out shell, 958) are two different things one letter apart, and in the

  worth a line in that area's next sweep rather than a frontend workaround.

## Drift for CLAUDE.md

Not applied — the branch of a propose-only night carries this file and nothing
else. Both are one-sentence fixes.

1. **CLAUDE.md:705** — "every rule styling the conversation is scoped by
   *container* (`#pty-pane.native …` / `#agent-popout …`) rather than written as
   its own class" is backwards, and it inverts the invariant it sits inside. The
   conversation's own rules — `.agent-turn`, `.agent-who`, `.agent-said`,
   `.agent-tool`, `.agent-note`, `.agent-card`, `#agent-log`, `#agent-composer`,
   `#agent-input`, `#agent-send` (index.html:792–891) — are written **unscoped**,
   which is precisely what lets one subtree look right in either container. Only
   the per-container *differences* carry a prefix: `#pty-pane.native #agent-body`,
   `#agent-popout #agent-log`, `#agent-popout:not(.editing) #agent-composer`,
   `#agent-popout #pty-mcp`. A session that followed the sentence as written
   would scope a new conversation rule to one container and break the other.
   index.html:908–910 states it correctly for its own block; CLAUDE.md
   generalised a local note into a global rule and reversed it doing so.

   Suggested: "every rule styling the conversation itself is written on the
   body's own classes and left *unscoped*, so it holds in either container; only
   the differences between them carry a `#pty-pane.native …` / `#agent-popout …`
   prefix".

2. **CLAUDE.md:264** — "They are injected by `app.js` on the pane's **first
   open**". They are injected on the first open of the **terminal surface**
   (`loadTerminalVendor` 3773 is called only from `openPane`'s non-native arm,
   3881). The default surface is native, so a launch that opens the pane every
   day parses none of the 289 KB. The claim understates the win and misdescribes
   the trigger. index.html:1836 carries the same imprecision.

3. **CLAUDE.md:877 and SKILL.md:66** — "5,700 lines" is 6,498. Raised in the
   2026-08-11 findings and still standing; noting it again rather than letting it
   drift a third time.

4. Two comments inside the area, for whoever lands A:
   - app.js:5268 — "Both paths end at `closePane`, which is what makes D12 one
     rule rather than two" is true only on the terminal surface today.
   - app.js:5239 — "Zoom is claimed above everything, Escape included, and above
     the terminal's own keys only because that branch returned first" reads as
     its own opposite. Zoom is claimed *below* the terminal branch, because that
     branch returns first.
