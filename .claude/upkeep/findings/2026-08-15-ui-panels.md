Five pieces of drift.

**D1 — `installFindCss` does not exist.** Named at index.html:1010 and
index.html:1439, and once more at `perf/harness/ui-check.mjs:840`. The functions
are `findCssOn` / `findCssOff` (app.js:2381, 2385). The same comment is wrong a
second way: it says the rules are written "the first time `/` is pressed and
empty until then", but `openFind` fills `#find-css` on *every* open and
`closeFind` empties it on every close — that withdrawal is load-bearing, it is
the fix for the lingering-paint bug documented at app.js:2410. The perf argument
for keeping the rules out of the sheet is untouched. Proposed for 1439:

> Find-match painting, written into by `findCssOn` whenever the bar is open and
> emptied by `findCssOff` when it closes — see `closeFind` for why the
> withdrawal has to happen in that order.

and for 1010, `… — see the comment on that element and `findCssOn` in app.js.`

**D2 — "Three tabs over one payload from `get_settings`"** (app.js:5157). There
are four: Keys, Window, Themes, Custom theme (index.html:1901–1904, and
`selectPane` dispatches on all four). One word.

**D3 — the outline panel's markup comment says the opposite of its CSS.**
index.html:1803 reads "Left edge of the reading area, so it can sit open
alongside the stack panel on the right rather than fighting it for the slot."
The rule is `position: absolute; top: 8px; right: 8px` (1030) — it is on the
right, and overlapping is deliberate: its own CSS comment says so (1020–1025,
"It also overlaps `#stale-rail` and, when both are open, `#stack-panel` — hence
the z-index above both"), and `PANES` says so again (app.js:1848–1852, "a
transient overlay floating at `right: 8px` *above* the stack rather than beside
it"). No `left: 8px` appears anywhere in this repo's history for it, so the
markup comment appears to have been wrong from the start. It is the worst kind
of line here — it reads as a design reason and would send a future session
looking for a bug in the geometry. Proposed replacement:

> Last of the right-hand overlays and drawn above them: it floats over the
> stack panel rather than beside it, because it is the shortest-lived thing on
> screen. See its rule for why overlapping is the cheaper trade.

## Pass 2 — simplify

Three, all small. The area is in good shape: no dead top-level function in
`app.js` (all 262 checked for a second reference), no `id` in `index.html`
unreachable from CSS or script, and no CSS class in the structural sheet that
nothing applies — `.oi` and `.l1`–`.l6` reach the DOM through a template literal
in `buildOutline` and were the only ones that looked orphaned.

### F1. `mark.hl.stale` is unreachable, and its print counterpart is redundant twice over

The 2026-08-11 sweep established that `wrapRange`'s `stale` parameter is dead —
all four call sites pass `false` (1072, 1132, 1170, 1400), because
`applyHighlights` sends a stale mark to the rail and `continue`s before any
placement runs. Re-verified today: still four call sites, still all `false`. The
CSS end of that is in this area:

- `mark.hl.stale` (index.html:361) matches nothing that can exist.
- `#content mark.hl.stale` (1567) is redundant *even if it could* — the line
  above it, `#content mark.hl`, already matches an element carrying both
  classes.

```diff
-      mark.hl.stale { background: var(--stale, #ef6a7d); color: var(--stale-text, #1a1a1a); }
```
```diff
-        #content mark.hl,
-        #content mark.hl.stale {
+        #content mark.hl {
           background: none; color: inherit; padding: 0; outline: none;
         }
```

−2 lines. The second hunk is safe on its own. **The first is not a two-line
decision**, and this is the reason it stays a proposal rather than becoming the
one edit this sweep could have argued for:

`mark.hl.stale` is the *only* reader of `--stale-text` anywhere in the tree. All
ten bundled palettes declare it (`ui/themes/*.css`, both mode blocks each), and
`README.md:481` lists it among the custom properties a theme may set. Deleting
the rule leaves a documented, universally-declared property that nothing reads —
and a theme CSS custom property is public surface under this job's own
invariants. So the honest options are: delete rule and property together
(README, ten palettes, a `ui-style` sweep's call, not this one), or keep the
rule as the declared contract for a state the code no longer produces and say so
in the comment. Either way it wants the same commit as `wrapRange`'s parameter,
or the rule and the branch go on justifying each other.

### F2. `WINDOW_TOGGLES` carries two platform flags where one does the work

`mac` and `macOnly`, filtered as `if (isMac ? !t.mac : t.macOnly) continue;`
(5505). Across the three rows the two flags never disagree: `{mac: false}` twice
and `{mac: true, macOnly: true}` once, which is exactly `mac !== isMac`. The
block comment above already describes the one-flag reading — "`mac` is which
platform a row belongs to, and both directions are used" — and does not mention
`macOnly` at all.

```diff
-    mac: true,
-    macOnly: true,
+    mac: true,
```
```diff
-    if (isMac ? !t.mac : t.macOnly) continue;
+    // `mac` is the platform the row belongs to; there is no row for both.
+    if (t.mac !== isMac) continue;
```

−1 line and one less concept. **Behaviour delta, and it is why this is a
proposal:** the two-flag form can express "shown on both platforms"
(`mac: true, macOnly: false`) and the one-flag form cannot. No row uses it, and
the comment says a row belongs to one platform — but if a future toggle is meant
for both, this makes that a three-line change rather than a field.

### F3. `renderBlockPicker` parses the draft palette twice

app.js:5804: `if (!blocksOf(draft.css).light && !blocksOf(draft.css).dark) return;`
— two full scans of the CSS for one question.

```diff
-  if (!blocksOf(draft.css).light && !blocksOf(draft.css).dark) return;
+  const blocks = blocksOf(draft.css);
+  if (!blocks.light && !blocks.dark) return;
```

Net 0 lines. Not a hot path — it runs on opening the Custom tab and on switching
block — so this is tidiness, not speed.
